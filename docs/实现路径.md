## 1. 调研阶段：先确定"能做什么"

**问题**：方案的完整架构（路由层/缓存/validator）要落在哪？Hermes 自身支持多少？

**动作**：

1. 加载 `hermes-agent` 技能 → 读 `references/providers-and-models.md`
2. 查本机 `~/.hermes/config.yaml` 与 `hermes config list`

**发现**：

| 能力 | Hermes 原生支持？ |
|------|------------------|
| 多 Provider（35+，含 custom）| ✅ |
| Fallback 链（`hermes fallback`）| ✅ |
| 模型别名（`/model` 切换）| ✅ |
| 凭据池轮询 | ✅ |
| **按任务自动路由** | ❌ |
| **语义缓存** | ❌ |
| **辅助模型（compression 单独指定小模型）** | ❌（压缩走主模型）|
| **validator 升级重跑** | ❌ |

**决策点 1**：Hermes 原生能力覆盖不到方案核心（自动路由/缓存/校验）

→ **选择**：**自建一个 OpenAI 兼容的路由代理**，Hermes 的 `model.base_url` 指向它。
→ **理由**：Hermes 只需认一个 OpenAI 端点，所有复杂逻辑放在代理层，**不动 Hermes 源码**，可随时回滚。

## 2. 骨架搭建：OpenAI 兼容代理

**技术选型**：Python + FastAPI + httpx（异步）+ PyYAML

**文件划分**（单一职责，便于排查）：

```
router.py     主程序（端点、路由调用、观测）
providers.py  Provider 池（限速/熔断/fallback）
routing.py    路由决策（特征提取 + 规则匹配 + 数据分级）
cache.py      缓存层（精确 + 语义）
validator.py  校验层（输出质量把关）
config.yaml   唯一需要改的配置
```

**决策点 2**：流式（stream）怎么处理？

Hermes 主链路**全部是流式**（终端/微信流式输出）。

→ **选择**：连接阶段可切换（未开始输出前失败可换 provider），**一旦开始输出就直接透传**（无法回退）。
→ **理由**：流式请求无法"撤回重试"，硬重试会造成重复输出；测延迟时也发现流式首字仅 0.49s，切 provider 的收益不值这个复杂度。

**决策点 3**：代理怎么连不同厂商？

- DeepSeek：**国内直连**（快）
- Groq / OpenRouter / Gemini：**必须走代理**（国内不通）

→ **选择**：**双 httpx 客户端**（proxy / noproxy），按 provider 配置切换。
→ **理由**：若全部走代理，DeepSeek 也会变慢；实测直连 1.0s vs 代理后 1.5s+。

## 3. Provider 池：重试分类是灵魂

按方案第 11 章实现后，**实测发现两个必须修的问题**：

### 问题 A：兜底 provider 被误熔断

**现象**：`/health` 显示 `deepseek banned_for: 599`（被熔断 10 分钟）
**危害**：兜底被熔断 → 请求 fallback 到**慢的免费池** → **性能反而退化**（与目标相反）
**修复**：config 加 `no_breaker: true`，`CircuitBreaker.record(exempt=True)` 只统计不熔断

> **决策点 4**：熔断器要不要覆盖兜底 provider？→ **不覆盖**。兜底是最后防线，宁可承担慢响应也不能"拒绝服务"。

### 问题 B：流式请求是观测盲区

**现象**：微信会话（Hermes 主链路全流式）延迟记录为 `None`
**危害**：看不到真实性能，无法判断是否退化
**修复**：流式分支补 `latency` 记录 + 计入熔断统计

## 4. 路由层：规则先于分类器

按方案第 4.2 章"先硬编码规则"，但同时按**实测数据**调整：

| 规则 | 触发条件 | 为何这样设计 |
|------|---------|-------------|
| `background_summarize`（优先级最高）| 无工具 + 长输入 + 压缩/摘要关键词 | 后台任务**用户无感延迟**，是省 token 的最佳切入点 |
| `simple_task` | 无工具 + **长输入（3k-60k）** + 翻译/改写等关键词 | **关键调整**：短请求不走免费池 |
| `long_context` | 无工具 + >30k tokens | 需要长上下文模型 |
| `default` | 其余（含所有带工具请求）| Agent 能力必需，且延迟敏感 |

> **决策点 5**：短请求要不要走免费池？
> **最初设计**：走（按方案 L1 定位）
> **实测后改**：**不走**。免费池（境外）走代理实测 12-24s，DeepSeek 直连 1s——**短请求 token 消耗小，"省几分钱换 20 秒等待"是亏的**。
> **新原则**：**只有 token 大户（长输入）才值得等**。

## 5. 接入 Hermes：三个陷阱

### 陷阱 1：改 provider 会打断 cron 任务

切到 `provider: custom` 时，Hermes 警告：**2 个 enabled cron 任务的 provider_snapshot 与新全局值不一致，将 fail closed**。

→ **解法**：**不改 provider，只改 `base_url`**（provider 保持 `deepseek`）——流量照样走代理，cron 快照不受影响。✅

### 陷阱 2：agent 无法从内部重启网关

尝试了 3 种方式（`launchctl kickstart` / `launchctl submit` / Hermes cron 脚本），**全部被系统正确拦截**：

> "command cannot restart or stop the gateway from inside the gateway process"
> "prevents agent-driven SIGTERM-respawn loops"

→ **解法**：做成**桌面双击脚本**（`重启Hermes网关.command`），由用户从外部触发。✅
→ **认知**：这是**合理的安全设计**——agent 不该有权重启自己的宿主。

### 陷阱 3：pkill 匹配不到进程

`pkill -f "hermes-token-router/.venv/bin/python"` 杀不掉，因为进程命令行是**相对路径** `.venv/bin/python router.py`。

→ **解法**：用 `pkill -f "router.py"` 或直接按 PID kill。✅

## 6. 缓存层：先划安全边界

**双层设计**：

| 层 | 实现 | 实测 |
|----|------|------|
| 精确 | prompt 规范化 SHA256 | **0.019s（131×）** |
| 语义 | 硅基 `Qwen3-Embedding-0.6B` + 余弦 ≥0.97 | **0.131s（21×）** |

> **决策点 6**：哪些请求可以缓存？
> **硬规则**：**只有"无工具 + 非流式"请求**（压缩/摘要/翻译/分类）。
> **理由**：带工具的请求上下文强相关（每轮不同），缓存会返回**错误结果**——这是安全性问题，不是性能问题。

---

## 7. 校验层：不合格就升级，不原地重试

**校验项**（全部规则化，毫秒级，不额外调模型）：
- 非空（防"token 被思考吃光"）
- JSON 契约（要求 json 必须可解析）
- 长度合理性（长输入却输出 <20 字 = 疑似敷衍）

**升级策略**：不原地重试 → **直接换 DeepSeek 重跑**，最多 1 级。

> **决策点 7**：为什么不重试原模型？
> **依据方案第 11.1 章**：同一模型重跑大概率还是错（能力性失败），纯浪费 token 和时间。

## 8. 关键发现：一个参数省 95%

**实测数据**（同一摘要任务）：

| 配置 | 延迟 | tokens |
|------|------|--------|
| Qwen3 默认（开思考）| 19.5s | 393 |
| **+ `enable_thinking: false`** | **0.71s** | **19** |

**两个字回复消耗 393 tokens**——推理模型的"思考税"是隐形 token 大户。

**落地方式**：在 provider 配置里支持 `extra` 参数注入：

```yaml
siliconflow:
  extra:
    enable_thinking: false
```

## 9. 完整决策记录表

| # | 决策 | 备选 | 选择 | 依据 |
|---|------|------|------|------|
| 1 | 架构落地方式 | 改 Hermes 源码 / 自建代理 | **自建代理** | 不侵入、可回滚 |
| 2 | 流式处理 | 强制非流式重试 / 连接期切换 | **连接期切换 + 已输出直透** | 流式无法撤回 |
| 3 | 网络策略 | 全部走代理 / 双客户端 | **双客户端** | DeepSeek 直连更快 |
| 4 | 熔断覆盖范围 | 全部 provider / 兜底豁免 | **兜底豁免** | 兜底必须永远可用 |
| 5 | 短请求是否降级 | 是（按方案）/ 否 | **否** | 实测延迟代价 > 省钱价值 |
| 6 | 缓存范围 | 全部 / 仅无工具非流式 | **仅无工具非流式** | 带工具缓存会错 |
| 7 | 失败重试 | 原地重试 / 升级重跑 | **升级重跑（≤1 级）** | 能力性失败重试无用 |
| 8 | Hermes 接入方式 | 改 provider / 只改 base_url | **只改 base_url** | 避免 cron 快照冲突 |
| 9 | 网关重启 | agent 内部重启 / 用户外部触发 | **用户双击脚本** | 系统安全机制（合理）|

## 11. 复盘：这次做对了什么

1. **先调研再动手**——如果没查清 Hermes 的能力边界，可能白写一套路由再发现位置不对
2. **实测优先于方案**——方案里的模型名全下架了；"短请求走 L1"经实测被推翻
3. **性能是隐性成本**——省 token 若带来 20s 延迟，用户会跑掉；**先保证体验，再谈省钱**
4. **安全边界明确**——缓存只碰无工具请求、敏感数据强制走付费，这些规则先于性能优化
5. **可回滚是底线**——改全局配置前备份、准备一键回滚、单点服务用 KeepAlive 兜住
